# Results

Resume-ready claims, each traceable to a measured number. Every figure below
comes from [`docs/ACCURACY_REPORT.md`](./docs/ACCURACY_REPORT.md), which is
generated by `npm run accuracy:report --workspace server` over the 704-row
synthetic dataset (2026-03 to 2026-09). Nothing here is estimated by eye — the
"Where it comes from" column names the row in that report, and anything derived
shows its arithmetic.

## The bullets

- **Automatically categorized 97.1% of 701 transactions correctly, with zero
  miscategorizations** — every row the engine committed to, it got right; the
  remaining 2.9% were routed to a review queue rather than guessed at.
- **Cut the transactions a person has to touch by 97.1%, from 701 to 20** —
  roughly one row in 35 needs a human, instead of every row.
- **Detected 4 of 4 planted anomalies** — two large one-off purchases, a
  subscription price rise, and a newly-appearing recurring charge — using
  deterministic statistics, no model call, so results are reproducible.
- **Identified 13 of 13 recurring monthly bills with no false positives across
  69 everyday merchants**, including a daily coffee habit that looks like a
  subscription from a distance.
- **Caught 6 of 6 duplicate rows from simulated bank sync glitches** while
  correctly surfacing — rather than silently dropping — 4 legitimate same-day
  repeat charges for the user to resolve.
- **Held categorization cost to one model call per unresolved merchant, not per
  transaction**, by settling everything a deterministic rule can settle first.
- **Achieved 100% parse success on 704 rows** across mixed date formats, sign
  conventions and merchant-string noise, with 0 parse errors.

## Two numbers deliberately not turned into a bullet

**Anomaly-flag precision, 55.6% (5 of 9 flags trace to a planted edge case).**
This one is real and reported, but it does not mean 4 flags were wrong. The
detectors are deterministic — a flagged month genuinely did spend 367% above its
own three-month baseline. The four unplanted flags are listed in full in the
report with their explanations, and whether any of them deserves a person's
attention is a judgement the script cannot make. Quoting "55.6% precision" as if
the rest were errors would be the wrong claim; quoting "100% precision" by
counting them as correct would be a flattering one. So the report shows both
numbers and the four explanations, and the resume bullet above claims only
detection recall (4/4), which is unambiguous.

**"97.1% accuracy" could trivially be 100%.** All 20 unresolved rows are a
single merchant, `THE HALL`, whose name says nothing about what it sells. One
merchant-specific rule would clear them and take the headline to 100% — and it
would mean nothing except that the test set had been memorised. The queue is the
honest answer for a genuinely ambiguous string, and the LLM fallback exists for
exactly this tail.

## Reproducing these

```bash
npm run db:seed        --workspace server   # load the synthetic dataset
npm run accuracy:report --workspace server  # regenerate docs/ACCURACY_REPORT.md
```

The report needs no database and no API key: it runs the deterministic pipeline
in-process over the CSV and scores it against the ground truth recorded by the
generator in `server/prisma/seed-data.ts`. Any change to the rules or the
normalizer moves the numbers immediately, which is the point — these figures are
a test, not a claim someone typed.
